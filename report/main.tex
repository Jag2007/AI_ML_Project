\begin{abstract}
``Two things move together'' does not mean ``one causes the other''. The Corr2Cause dataset tests exactly
this. Each example gives a short text (the premise) that says which variables are related, and a claim (the
hypothesis) such as ``A directly causes B''. The task is to say if the claim is surely true (1) or not (0). We
built a five-step pipeline, one notebook per team member: clean the data, turn the text into a causal graph with
the PC algorithm, build features, train classifiers, and finally build a DAG and ask it ``what if''
(intervention) questions with a Bayesian network. With text features (TF-IDF) alone, logistic regression gets an
F1 of only 0.47. Adding features from the causal graph raises it to 0.88. The graph step alone, with no learning,
reproduces 98.5\% of the test labels. Our final model, a Random Forest, gets a test F1 of 0.957. 89\% of the
cause arrows it draws are correct, and its graphs answer 92 of 96 intervention questions correctly.
\end{abstract}

\section{Introduction}
\textbf{The problem.} Ice cream sales and drowning cases both go up in summer. They are \emph{correlated}, but
ice cream does not cause drowning; hot weather causes both. Large language models often make this mistake and
treat correlation as causation.

\textbf{The dataset.} Corr2Cause~\cite{jin2024} turns this into a yes/no task. A real example (shortened):
\begin{quote}\small
\emph{Premise:} There is a closed system of 3 variables, A, B and C. A correlates with B. A is independent of C.
B is independent of C.\\
\emph{Hypothesis:} There is a common effect (collider) of A and C.\\
\emph{Label:} 0 (not valid)
\end{quote}
The premise says which pairs are related (``correlates'') and which are not (``independent''). The hypothesis
is a cause-and-effect claim. The label is 1 only if the claim is true in \emph{every} causal graph that fits the
premise. If even one fitting graph breaks the claim, the label is 0.

\textbf{Our goal.} We did not want a black box. We wanted every prediction to come from a graph we can draw and
explain. So we combined a classic causal discovery method (the PC algorithm) with simple machine learning models.
This is a \emph{neuro-symbolic} design: the learned part reads the text, and the symbolic part (the graph) does
the exact reasoning.

\section{Related Work}
\textbf{Causal graphs.} Pearl~\cite{pearl2009} showed how to reason about cause and effect with directed acyclic
graphs (DAGs) and Bayesian networks. Verma and Pearl~\cite{verma1990} showed that different DAGs can give the
same independences when they have the same skeleton (links without direction) and the same colliders. So from
independences alone we can only find a group of DAGs, called the \emph{Markov equivalence class} (MEC). The PC
algorithm~\cite{spirtes2000} finds this class from independence facts, and Meek's rules~\cite{meek1995} set every
arrow direction that is forced.

\textbf{Finding causes in text.} Early systems found cause--effect pairs with hand-written patterns~\cite{khoo2000}.
SemEval-2010 Task~8~\cite{hendrickx2010} and BECauSE~2.0~\cite{dunietz2017} label causal phrases in sentences.
These works find \emph{what a text claims}. They do not check if the claim \emph{follows} from the evidence, and
they do not build a graph.

\textbf{Causal reasoning tests for language models.} The Corr2Cause authors~\cite{jin2024} found that 17 large
language models score close to chance. Fine-tuned models score well, but fail when the sentences are reworded or
the variable names are changed, so they learn surface patterns, not reasoning. CLadder~\cite{jin2023cladder} asks
similar causal questions, but only tests models and does not give a pipeline.

\textbf{Neuro-symbolic AI.} These systems let a learned part read the input and a rule-based part do exact
reasoning~\cite{garcez2023}. Our pipeline follows this idea. Table~\ref{tab:lit} sums up the gap we fill.

\section{Key Ideas}
\textbf{DAG.} A directed acyclic graph: arrows mean ``directly causes'', and you can never follow the arrows back
to where you started (no cycles, no self-loops).

\textbf{Collider and confounder.} In X$\to$Z$\leftarrow$Y, Z is a \emph{collider} (common effect). In
X$\leftarrow$Z$\to$Y, Z is a \emph{confounder} (common cause).

\textbf{Conditional independence.} ``A and C are independent given B'' means that once we know B, knowing A tells
us nothing more about C. The premises list these facts, and the PC algorithm uses them.

\textbf{Markov equivalence class and mec\_support.} Many DAGs can fit one premise. For each claim we count in how
many of them it is true:
\begin{equation}
\text{mec\_support} = \frac{\text{fitting DAGs where the claim is true}}{\text{all fitting DAGs}}.
\label{eq:mec}
\end{equation}
If mec\_support $=1$, the claim holds in every fitting DAG, so it should be valid. We call ``predict valid when
mec\_support $=1$'' the \emph{symbolic rule}. It uses no learning.

\textbf{Intervention.} Forcing a variable to a value is written $do(X)$. This is different from just observing X.
We measure the effect of X on Y as
\begin{equation}
\text{effect} = P(Y{=}1 \mid do(X{=}1)) - P(Y{=}1 \mid do(X{=}0)).
\label{eq:effect}
\end{equation}
If Y is not downstream of X in the graph, the effect is 0.

\textbf{Evaluation.} From the confusion matrix (TP, FP, FN, TN):
\begin{equation}
P = \frac{TP}{TP+FP},\qquad R = \frac{TP}{TP+FN},\qquad F_1 = \frac{2PR}{P+R}.
\label{eq:f1}
\end{equation}
Precision ($P$): of the claims we called valid, how many really were. Recall ($R$): of the truly valid claims, how many we
found. F1 balances the two.

\section{Step 1: Cleaning the Data (Notebook 01)}
We used the official train, validation and test splits from Hugging Face (Table~\ref{tab:data}). Each row has
the text (\texttt{input}), the \texttt{label}, the number of variables, and a \texttt{template} that says which
type of claim it is.

\textbf{Checking.} We looked at \texttt{head()}, \texttt{tail()}, the shape and the column types, and counted
missing values and duplicates. There were none, so nothing had to be filled in or dropped.

\textbf{Cleaning.} Every text has exactly one ``Hypothesis:'' marker, so we split it into a \texttt{premise} and
a \texttt{hypothesis} column and removed extra spaces. We checked that the number of variables written in the
premise matches the \texttt{num\_variables} column. The same premise is reused with up to 90 claims, so we gave
each premise an ID.

\textbf{Removing data leakage.} A few premises were in two splits at once (2 in train and validation, 3 in
validation and test). If the model sees a premise in training and again in testing, its score looks better than
it really is. We kept the test set as it was and removed the shared premises from train and validation.

\textbf{Subsampling train.} Train has about 206{,}000 rows, which is slow. We randomly picked 400 whole premises
(seed 42) with all their claims, giving 35{,}340 rows. The share of valid claims stayed the same (18.5\%).

\label{fig:eda}

\textbf{Class imbalance.} Only 13--19\% of claims are valid (Fig.~\ref{fig:eda}, left). A model that always says
``not valid'' would already be over 80\% accurate, so accuracy is misleading. We use precision, recall and F1
(Eq.~\ref{eq:f1}), and we set \texttt{class\_weight="balanced"} so the rare valid class counts as much as the
common one.

\textbf{A hidden shortcut.} ``Child'' claims are never valid (Fig.~\ref{fig:eda}, right), yet their text
(``X directly causes Y'') is the same as ``parent'' claims. So the \texttt{template} column gives away the label.
We never use it as a feature, only to study mistakes.

\textbf{Harder test set.} Train only has graphs with 5--6 variables, but validation and test also have 2--4
variables. So the test set has cases the model never saw.

\section{Step 2: Text to Graph (Notebook 02)}
\textbf{Parsing.} The sentences follow fixed templates, so regular expressions (regex) read them exactly. From each
claim we take the two variables (the single capital letters) and the claim type (direct cause, indirect cause,
collider, confounder) from keywords. We added schema checks: variables must be A--F and appear in the premise, no
self-loops (A$\to$A), and no unknown wording. All real rows passed, and broken examples we wrote by hand were
caught.

\textbf{PC algorithm.} PC normally tests independence on numeric data. Here the premise already states the
independences, so pgmpy's PC reads them directly (\texttt{ci\_test="independence\_match"}). PC (1) starts with
every pair linked and removes the link between independent pairs, (2) finds colliders X$\to$Z$\leftarrow$Y, and
(3) uses Meek's rules to set more directions. Links it cannot decide stay undirected (Fig.~\ref{fig:pc}).

\begin{figure}[t]
\centering
\includegraphics[width=\linewidth]{pc_graphs}
\caption{PC output for two premises. Solid arrows have a known direction; dashed lines could point either way.
Left: E is a common effect of A--D. Right: only A and B are linked, and C stands alone.}
\label{fig:pc}
\end{figure}

\textbf{All fitting DAGs.} For each undirected link we try both directions. We keep every version that has no
cycle and is I-equivalent to the PC graph (same skeleton and colliders). This gives every DAG in the Markov
equivalence class, between 1 and 144 per premise. For each claim we then compute mec\_support (Eq.~\ref{eq:mec}).

\textbf{What does each claim mean?} Our first definitions were the textbook ones: a collider is a shared direct
child, a confounder is a shared direct parent, and ``X causes something else which causes Y'' means Y is
downstream of X but not a direct child. To match the labels better, we read the code that made the
dataset~\cite{corr2causecode}. It looks at every path between X and Y and names it by its arrows
(Table~\ref{tab:claims}). The main difference: ``X causes something else which causes Y'' only needs a path of two
or more arrows, even if X$\to$Y also exists.

\begin{table}[t]
\centering
\caption{Claim definitions used by the Corr2Cause generator}
\label{tab:claims}
\footnotesize
\begin{tabular}{ll}
\toprule
Claim & Path between X and Y \\
\midrule
X directly causes Y & X$\to$Y \\
X causes sth.\ else which causes Y & X$\to\dots\to$Y (2+ arrows) \\
Collider (common effect) & X$\to\dots\to$Z$\leftarrow\dots\leftarrow$Y \\
Confounder (common cause) & X$\leftarrow\dots\leftarrow$Z$\to\dots\to$Y \\
\bottomrule
\end{tabular}
\end{table}

(mec\_support $=1$) matches the label, with no learning at all.

label noise.

\section{Step 3: Feature Engineering (Notebook 03)}
A model needs numbers, so we turn each claim into a row of features.

\textbf{Structured features (15).} The claim type, one-hot encoded (the types have no order); the number of
correlations and independences in the premise; whether X and Y correlate, are independent, or are independent
given other variables; whether PC drew X$\to$Y, Y$\to$X or an undirected X--Y; the number of fitting DAGs on a log
scale (\texttt{log\_mec\_size}); and mec\_support. There were no missing values. The columns have different
ranges, so we standardised them with \texttt{StandardScaler}: each value becomes
(value $-$ mean) / standard deviation, with the mean and standard deviation taken from train only.

\textbf{Text features.} TF-IDF gives each word or word pair (unigrams and bigrams) a score: high if it is common in
this text but rare in the others. We made one TF-IDF table for the premise (135 terms) and one for the hypothesis
(106 terms), fitted on train only. We kept one-letter words because A--F are the variable names.

\textbf{Feature selection.} We ranked text terms with the chi-squared test and structured features with mutual
information (how much a feature tells us about the label, Fig.~\ref{fig:mi}). mec\_support is far ahead, followed
by the arrow-direction features. The top text terms are words like ``collider'' and variable letters, which say
nothing about the pair being asked about. Keeping only the top 50 + 30 text terms changed F1 by about 0.02 (0.88
vs 0.90). With only 19 validation premises this is within the noise, so we kept all terms.

\begin{figure}[t]
\centering
\includegraphics[width=0.82\linewidth]{mutual_information}
\caption{Mutual information of each structured feature with the label (train). mec\_support, which comes from PC,
is clearly the most useful.}

\textbf{Text vs graph features (ablation).} Table~\ref{tab:ablation} trains the same logistic regression on three

a linear model with balanced class weights cannot copy the sharp step at exactly mec\_support $=1$. The tree models
in Step~4 can.

\section{Step 4: Models and Evaluation (Notebook 04)}
\textbf{Setup.} Each claim becomes 256 features (135 + 106 TF-IDF + 15 structured). We tried logistic regression,
Random Forest (300 decision trees that vote) and gradient boosting (small trees added one by one, each fixing the
last one's mistakes). We tuned the hyperparameters with \texttt{GridSearchCV} and 5-fold cross-validation, scored by
F1. We used \texttt{GroupKFold}, which keeps all claims of one premise in the same fold, so the model is never
checked on a premise it trained on. Table~\ref{tab:tuning} shows the settings tried and the best ones.

\textbf{Results.} Random Forest had the best validation F1, so we chose it (Table~\ref{tab:results}). It is a bit
better than the symbolic rule on validation (0.929 vs 0.906) and test (0.957 vs 0.952), but the test gap is inside
the confidence interval below. So the graph step does almost all of the work, and the learned model mainly tidies
up the edges of the rule.

\textbf{Confidence interval.} The test set has only 21 premises. Rows of the same premise are not independent, so
we used a bootstrap over premises: we resampled whole premises 1{,}000 times and recomputed F1 each time. The 95\%
confidence interval (2.5th to 97.5th percentile) is 0.921 to 0.982.

\textbf{Error analysis.} The model made 16 mistakes out of 1{,}162 (Fig.~\ref{fig:cm}). Half are false positives on
``parent'' claims, the same label noise found in Step~2. It made no mistakes on ``child'' claims. Graphs with 2--4
variables, which never appeared in training, had 1 mistake in 126 rows, about as low as the 5--6 variable graphs.
This is because the structured features come from the parser and PC, not from memorised sentences.

\section{Step 5: DAG and Bayesian Network (Notebook 05)}
\textbf{Building the DAG.} For each test premise, every ``X directly causes Y'' claim predicted valid becomes an
arrow. We add the most confident arrows first. An arrow is skipped if it is a self-loop, uses a variable not in the
premise, or would create a cycle. All 21 test graphs are proper DAGs.

\textbf{Edge precision.} Edge precision = correct arrows / arrows drawn, and edge recall = correct arrows / true
arrows. We drew 73 arrows and 65 are correct (\textbf{edge precision 0.89}), and no true arrow was missed (edge
recall 1.00). Against the PC graph the edge precision is 1.00: all 8 wrong arrows are ones PC supports but the
dataset labels as 0 (Fig.~\ref{fig:dag}).

\begin{figure}[t]
\centering
\includegraphics[width=0.82\linewidth]{dag_vs_truth}
\caption{One test premise. Left: the true arrows. Right: our predicted DAG. Blue arrows are correct; the red
arrows are extra ones that PC supports but the dataset marks as not valid.}
\label{fig:dag}
\end{figure}

\textbf{Bayesian network.} A Bayesian network is a DAG with a probability table (CPD) at each node. Corr2Cause has
no numbers, so we made some: we gave the true graph random probability tables, simulated 5{,}000 rows from it, and
fitted our DAG on those rows with pgmpy. Then we measured intervention effects with Eq.~(\ref{eq:effect}).

\textbf{Why direction matters.} For the chain A$\to$B$\to$C, the true effect of A on C is 0.490, and the correct
graph fitted on the data gives 0.498. The reversed graph C$\to$B$\to$A fits the same data but gives 0.000 for A on
C, and wrongly says that C affects A (0.514).

\textbf{Intervention queries.} We used the five test premises where PC knows the full graph (only one DAG in the
class). For every ordered pair of variables we asked ``what is the effect of $do(X)$ on Y?'': 96 queries, 32 with
a real effect. A query is correct only if the graph gets both (1) whether there is an effect at all (a directed
path) and (2) its size within 0.05. We compare our DAG with two baselines fitted on the same data
(Table~\ref{tab:queries}).

\begin{table}[t]
\centering
\caption{Intervention queries on the five fully known test graphs}
\label{tab:queries}
\footnotesize
\setlength{\tabcolsep}{4pt}
\begin{tabular}{lccc}
\toprule
Graph & All queries & Real effects & Mean $|$error$|$ \\
\midrule
\textbf{Our predicted DAG} & \textbf{92 / 96} & \textbf{28 / 32} & \textbf{0.011} \\

\bottomrule
\end{tabular}
\end{table}

Our DAGs get 28 of the 32 real effects right; both baselines get none. So getting the arrows right, in the right
direction, is what makes the ``what if'' answers right.

\section{Conclusion and Next Steps}
Turning the text into a graph with a regex parser and the PC algorithm explains 97--98\% of the labels with no
learning. Adding these graph features to TF-IDF and training a Random Forest gives a test F1 of 0.957 (95\% CI
0.921--0.982), with no data leakage between splits. TF-IDF alone reaches only 0.47, which shows that word patterns
cannot replace causal reasoning. Most remaining mistakes come from a small set of labels that disagree with PC.

\textbf{Limitations.} Corr2Cause is made from templates, so our regex parser would not work on reworded or real
text. Train only has 5--6 variable premises. The Bayesian network data is simulated, not measured.

\textbf{Phase 2.} We plan to replace the regex parser and TF-IDF with a fine-tuned transformer that can read
reworded text, keep PC for the reasoning, and test on reworded and renamed-variable versions of the data, where the
Corr2Cause authors found fine-tuned models break down.
